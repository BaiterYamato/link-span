## Critério de classificação

Uma categoria principal por commit permite somar 24 sem dupla contagem. Nos commits mistos, a coluna descreve as facetas adicionais. Prevalece C quando há nova ligação nominal/formato de mod; depois B para capacidade genérica nova, A para incremento exclusivamente compatível de tabela pública, D para correção/implementação do host preservando a ABI C pública e E para build/fingerprint sem comportamento novo de gameplay.

A alteração de um overlay vanilla não basta para C: `En_Elf` despachando `oot.light.fairy` é B/D; `z_kaleido_item.c` condicionado por `LinkSpan_DynamicMovementInventoryMenuEnabled` é C. Comentários que citam o consumidor NEI/Unbound/CEL também não bastam. A identificação codificada de `unbound.json` e `formatVersion=2` no bootstrap, entretanto, é conhecimento específico do framework.

Contagem principal: **A=0, B=6, C=2, D=12, E=4**. A está presente como faceta em `b13913077`, `f811f71d6`, `d61b30877` e `a76045848`; esses commits também contêm C ou B. Não existe nesta lista um commit exclusivamente A. `5c4138b80` acrescenta campos à ponte C++ interna `NativeEscapeHatch`, não à tabela C pública `ShipNativeRuntime`; por isso é D com extensão interna documentada, e não prova de bump MINOR da ABI C. D significa preservação da ABI C pública: pode haver mudança de ponte interna, semântica operacional ou layout id, indicada na linha.

Os ids de oito caracteres são abreviações históricas. "Não pelo diff" significa que os arquivos de host daquele commit não alteram a entrada do hash sob a mesma toolchain/configuração; não comprova o id de uma build não examinada. `ExportSdk.cmake` no baseline e no HEAD inclui **todo** header de `soh/soh/native`, inclusive `OotNativeScenes.h` e headers C++ internos do core, além de `soh/include`; inclui também identidade/flags do compilador. Por isso uma correção D ou comentário E pode trocar o id sem quebrar o prefixo da ABI C.

## Itens C e limites da regularização

1. **b13913077 / OOT-CORE-008:** nova chamada nominal `SOH::Unbound::SequenceIdForPath` em `SetSoundSettingsFactoryXML`. O helper e os campos `unboundSongPath/unboundSongSeqId` já existiam no baseline; não é prova de que um framework novo foi inteiro compilado após o gate. O objetivo de música por caminho é genérico. Proposta: resolução/binding de sequência por caminho em uma interface de áudio genérica, com JSON do framework na DLL. Demonstração anterior de insuficiência e RFC específica: **não confirmado**.
2. **a76045848:** (i) função `LinkSpan_DynamicMovementInventoryMenuEnabled` e fluxo de equipamento no kaleido; (ii) reconhecimento de camada Unbound v2 e montagem especial após init no bootstrap. O primeiro já é dívida explícita em H/OOT-RELEASE-001.md:227,266-267; o segundo é classificação conservadora desta auditoria, confirmada pelo diff, sem handoff específico de insuficiência encontrado. Propostas: ownership/configuração genérica do menu de equipamento e montagem de camadas declarada pelo provider com fase e dono. A correção de rejeição em `4c45d5c3a` deve ser preservada nessa migração.

Detalhamento e condições futuras: [rascunho da RFC 0027](rfcs-draft/0027-host-rebuilds-after-coreext-gate.md).

Não foi confirmada RFC específica para cada capacidade histórica, nem a aprovação contemporânea de cada exceção. RFCs de mecanismo (0021/0023) não demonstram, sozinhas, insuficiência para cada chamada. Valores finais de rodada não foram atribuídos automaticamente a commits intermediários. O checklist do Gate OoT permanece aberto; aprovar documentação retrospectiva não substitui resolver/generalizar C nem testar o comportamento.
